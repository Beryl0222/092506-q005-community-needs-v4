# 社区需求补短板决策服务

面向“一刻钟便民生活圈”的需求采集与年度决策服务。核心原则是**先问居民再补业态**：
居民代表提交带证据的缺口，社区合并相似诉求，街道按人口覆盖、紧急程度与老幼服务权重
形成可解释候选项目；项目进入两年推进计划前须经街道、商户两级确认，预算冻结后分数
不可改，撤回或延期必须说明影响并通知相关社区。

服务只依赖 Python 标准库，数据保存在本地 SQLite，应用层通过进程内 JSON 适配器调用。

## 目录

- `src/community_needs/domain.py`：证据、诉求、评分卡、候选项目、计划项目等值对象。
- `src/community_needs/events.py`：规范化 JSON、内容哈希、追加事件与哈希链。
- `src/community_needs/store.py`：SQLite 持久化——事件日志、输入快照、命令日志。
- `src/community_needs/service.py`：应用服务（采集、评分、计划、确认冻结、撤回延期、重放）。
- `src/community_needs/api.py`：JSON 请求适配层。
- `tests/test_acceptance.py`：全部验收场景的可重复测试。

## 业务流程

```
居民代表提交带证据缺口            社区合并相似诉求            街道开年度周期+两年预算
 submit_demand ──────────────▶ merge_demands ──────────▶ open_cycle
       │                            │                        │
       │ 重复提交:命令幂等 /         │ 同类业态才能合并,        │ 权重可在开周期时
       │ demand_id 去重,不覆盖原件   │ 人口覆盖按合并组累加     │ 声明(默认 0.5/0.3/0.2)
       ▼                            ▼                        ▼
                 评分并固化输入快照            生成两年计划
                 score_candidates ────────▶ build_plan
                        │                        │
                        │ 评分卡 0-100,          │ 高分先排;当年装不下
                        │ 逐项给出三个分量        │ 排次年;两年都装不下→显式递延
                        ▼                        ▼
             街道确认 → 商户确认            预算冻结(两级确认齐全后)
             confirm_project(street)       freeze_budget
             confirm_project(merchant)           │
                                                 │ 冻结后 score_candidates/
                                                 │ build_plan 一律拒绝
                        ▼                        ▼
             审批人变更(只换责任人)      撤回/延期(说明影响+通知全部相关社区)
             change_approver             withdraw_project / delay_project
```

### 评分公式（可解释）

总分 0–100：

```
总分 = 0.5 × 人口覆盖分量 + 0.3 × 紧急程度分量 + 0.2 × 老幼服务分量
人口覆盖分量 = 合并组覆盖人口 / 本周期最大覆盖组人口 × 100
紧急程度分量 = 合并组最高紧急度(1-5) / 5 × 100
老幼服务分量 = min(1, (覆盖老人数 + 覆盖儿童数) / 覆盖人口) × 100
```

权重在开周期时可显式声明（和必须为 1），评分卡 `breakdown()` 同时给出公式、
权重、各分量原值与折算值，居民可以核对“为什么这个项目排前面”。老幼服务分量让
“声音不大但服务老人/儿童”的诉求不会被人口大盘淹没。

## 可解释与可重放是如何实现的

- **追加事件 + 状态重放**：`event_log` 只追加不修改，当前状态由事件归约得到。
  每条事件含 `prev_hash`，事件哈希 = sha256(前哈希 + 类型 + 规范化载荷 + 时间)，
  任何对历史事件的悄悄改动都会让 `verify_integrity()` 的哈希链校验失败。
- **输入快照（内容寻址）**：评分和排计划时把全部输入（诉求与证据、合并关系、
  覆盖人口、权重、两年预算、造价）固化为快照，`snap_<类型>_<内容哈希前16位>`。
  快照编号由内容决定，重放必然复现；`get_decision` 返回评分卡、两份快照全文与
  审批/变更/撤回事件轨迹。
- **命令日志与幂等**：所有写操作经 `Service.dispatch` 进入，携带 `command_id`
  的重复命令直接返回首次结果、不产生新事件；即使不携带编号也会自动记录。
  `replay_command_log()` 用原参数和原时间戳把命令重放进空库，比对事件哈希链、
  快照编号集合与最终状态投影，三者必须完全一致。
- **冻结不可改分**：冻结后重评、重建计划直接抛错；冻结后的撤回/延期是合规变更，
  必须给出原因，且通知集合必须覆盖全部受影响社区，同时记录影响（受影响社区、
  覆盖人口损失、释放预算、原计划年度），分数与其快照编号保持不变。

## 主要查询

| 动作 | 说明 |
| --- | --- |
| `get_demand` | 诉求详情、被合并的支撑诉求、合并组覆盖人口 |
| `list_candidates` | 候选项目排名与评分卡 |
| `cycle_status` | 周期预算、冻结状态、支出、递延项目与全部项目状态 |
| `list_decisions` | 每个决定使用的评分/计划快照编号与**当前**推进状态 |
| `get_decision` | 单项目完整溯源：评分卡、输入快照全文、审批变更轨迹、通知记录 |
| `list_notifications` | 按社区查询撤回/延期影响通知 |
| `verify_integrity` | 哈希链与快照内容校验 |
| `replay_command_log` | 命令重放一致性报告 |

## 验收场景对照

| 验收要求 | 测试位置 |
| --- | --- |
| 重放重复提交（幂等、去重不覆盖、证据必填、合并累加） | `重复提交与合并测试` |
| 跨年度排序（两年排期、已补齐诉求次年不再入候选） | `评分与两年计划测试` |
| 预算超支（当年/次年装不下的显式递延、支出不超预算） | `评分与两年计划测试` |
| 两级确认 + 预算冻结后不得改分 + 篡改可发现 | `确认冻结与审批人变更测试` |
| 审批人变更只换责任人不改分 | `确认冻结与审批人变更测试` |
| 撤回/延期说明影响并通知相关社区 | `撤回延期与通知测试` |
| 每个决定显示输入快照与当前推进状态 | `决定溯源测试` |
| 全流程命令重放后哈希/快照/状态一致 | `命令重放与接口测试` |
